The tested local implementation is substantially ahead of the old scaffold inventory in the identity, portfolio, employer, and assessment slices. Items marked REAL / TESTED are local evidence only, not a production-readiness claim. The current implementation preserves the existing publication API, makes `/u/{handle}` the shared-link format, and adds separately entitled portfolio customization.

### Current vertical slice contract and migration

- Existing `POST /api/v1/me/candidate-profile/handle` remains the handle-setting contract. A verified owner may change the handle before the first publication; afterwards a different handle returns `409 PROFILE_HANDLE_LOCKED`, even if the profile is unpublished. Re-submitting the same handle is idempotent.
- Existing `POST /api/v1/me/portfolio/publish` sets the lock in the same transaction as first publication. `GET /api/v1/me/portfolio` reports `public_handle_locked`; the public response remains unchanged and exposes no lock metadata.
- `GET /u/{handle}` serves the existing public profile page. Existing `/portfolio/{handle}` bookmarks continue to work. The frontend now advertises `/u/{handle}`.
- Migration `022_stable_public_profile_handles.sql` records the lock timestamp. It locks all existing non-null handles because the prior schema did not retain publication history after unpublishing; this avoids silently breaking potentially shared links. It does not delete or rename profile data.
- OpenAPI is generated from the FastAPI response models; the private portfolio response includes the handle lock flag, and public portfolio responses optionally include the active Pro design allowlist. Application snapshots are unchanged.

### Pro portfolio builder slice (migration 023)

- `GET /api/v1/me/entitlements` derives Candidate Pro from an active `portfolio_customization` grant; identity purpose and organization membership do not grant the feature. `POST /api/v1/me/portfolio/versions` requires a verified session, CSRF, active grant, strict template/theme/section validation, and an expected draft version. Versions are immutable; publishing can select a saved version for rollback.
- `GET /api/v1/me/portfolio/versions` is owner-scoped and remains available after downgrade. Premium design publication requires the Free profile to already be public. Existing Free profile publication does not require an entitlement.
- Public responses include only the active published design allowlist while the owner has the active entitlement. On downgrade, the profile remains public with the basic presentation and saved versions remain intact. No billing or upgrade flow is exposed.
- The builder is served at `/app/portfolio/builder` through FastAPI and the Next.js legacy wrapper. Preview and public rendering share `frontend/portfolio-renderer.js`; text is inserted with DOM text nodes, and public API data continues to exclude private projects and account identifiers.

### Opt-in employer discovery (migration 024)

- `GET/PATCH /api/v1/me/candidate-profile/discovery` exposes an owner-only preference. Enabling requires verified email, a completed candidate profile, an already published Free profile, CSRF, and the current `candidate-discovery-v1` consent. Discovery defaults off; disabling it or unpublishing the profile removes it from search.
- `GET /api/v1/organizations/{org_id}/candidates` requires a completed organization and owner/admin/recruiter membership. It returns only the candidate's public display name, target roles, skills, and `/u/{handle}` path; it excludes email, internal identifiers, private projects, evidence, and members of the searching organization. Search, pagination, no-store headers, and per-user/org rate limits are implemented.
- `/projects` contains the opt-in control; `/organization/candidates` provides the hiring-team search. API tests cover default-off consent, invalid and unauthorized requests, role/tenant boundaries, limited fields, idempotence, unpublishing, and republishing. Chromium covers opt-in through employer search.

### Account data export (synchronous MVP)

- `POST /api/v1/me/data-exports` requires an authenticated, verified account, CSRF, and the current password. It generates an allowlisted export inside a repeatable-read, read-only transaction, returns it as a dated JSON attachment with `no-store` and `no-referrer`, and audits success or reauthentication failure. Requests are limited to three per account per hour.
- The export includes account/terms, candidate profile, private and public projects/source links, portfolio settings/versions, current Pro entitlement, evidence, saved jobs, application snapshots/status history/evidence consent history, candidate-visible assessment invitations, the candidate's own workspaces/test runs, organization membership/invitations addressed to the account, and session timestamps. Credential hashes, tokens, other members' details, private employer test inputs, and platform audit records are excluded.
- The endpoint does not persist a second PII-heavy copy. A separate status/download resource is deferred because this MVP has no durable job worker; retrying the POST creates a fresh export. Uploaded artifacts and provider billing data are not available in the current product.

### Shared rate limiting (migration 025)

- All existing rate-limit call sites use a PostgreSQL-backed sliding window, so separate API workers share limits. Advisory transaction locks make concurrent checks for one key atomic; inactive buckets expire and are cleaned in bounded batches.
- Only an HMAC-SHA256 key digest is stored. Production startup requires `PROOFPATH_RATE_LIMIT_SECRET` to be at least 32 bytes and deployments must give every worker the same value. Secret rotation resets the rate-limit namespace; plan rotation deliberately.
- The limiter uses a separate short-lived PostgreSQL connection per limited request. This reuses the existing PostgreSQL service and avoids committing the request's business transaction to persist an attempt.

### Interview scheduling (migration 026)

- A hiring-team owner, admin, or assigned recruiter can schedule only for an active application at the interview stage. Creation is idempotent; interviewer slots are serialized in PostgreSQL and checked for overlaps across applications. Schedules require an offset-aware time between five minutes and one year ahead, a valid IANA display timezone, and an optional HTTPS meeting link without embedded credentials.
- Candidates see only their own schedules and can accept, decline, or request another time. Assigned hiring teams see the schedule and candidate response without candidate email. Updates use a version guard and reset a prior response; cancellation preserves the record and audit events. Earlier schedule values and responses are not available as a separate history feed. Withdrawal and final hiring decisions cancel active schedules.
- `/applications` and `/organization/applications` are connected to the list, response, schedule, reschedule and cancellation APIs. In-app notices appear when users next open their application page; interview email notifications and calendar integrations are not available.
- Candidate data exports include the candidate's schedule, meeting details, response and cancellation reason. Employer exports omit hiring activity that contains another candidate's personal data. Individual interview lookup endpoints reuse list responses; feedback notes are deferred until visibility and retention rules are established.

### In-app interview notifications (migration 027)

- Schedule, reschedule, cancellation and candidate-response events create unread notifications in the same transaction as the interview change. Candidate messages disclose no interviewer email, and hiring-team response notices contain no candidate identity or contact details.
- The notification list checks current candidate ownership or current organization role/application assignment, uses `no-store`, and supports marking one or all of the signed-in user's notifications read. Notification preferences and email delivery remain unconfigured.
- Candidate and employer application pages display notifications and let users mark them read. Candidate account exports include their notification contents and read state; employer exports include only their own generic notifications.

## Architecture and local database

[ADR 0001](adr/0001-fastapi-postgresql-modular-monolith.md) records the accepted first-stage architecture: FastAPI modular monolith, PostgreSQL, Psycopg, explicit SQL migrations, one user identity, purpose-specific onboarding, opaque server sessions, private artifacts, isolated execution, and bounded AI. Implemented API paths are versioned under `/api/v1`.

The local PostgreSQL service is reachable on loopback. A dedicated `proofpath_codex_app` role and separate `proofpath_codex_dev` and `proofpath_codex_test` databases were created for this checkout. Only PostgreSQL system catalogs were inspected; no pre-existing application data was read or changed. The local cluster trusts loopback connections, so these credentials/configuration are for development and tests only. The test suite refuses to truncate databases whose name does not end in `_test`.

## Implemented vertical slices

The API inventory currently marks 104 operations as implemented with typed contracts; it also includes the public competency catalog and application-scoped evidence sharing/report operations added outside the original inventory. Requirements use stable codes, explicit levels, accepted verification methods and freshness, and are frozen into each application at submission. `docs/API_STATUS.tsv` records inventory status; deferred operations have an explicit `DEFERRED` disposition.

Identity stores scrypt password hashes and only SHA-256 hashes of high-entropy verification, reset and session tokens. Verification/reset tokens expire and are consumed atomically. Password reset revokes every active session. Login returns only the next onboarding destination, not a global role. Authenticated mutations require the secure session cookie plus a matching CSRF cookie/header. PostgreSQL-backed shared rate limits cover registration, login, password reset, portfolio changes, public reads and hiring mutations. The HMAC secret must be configured consistently across production workers.

Account session management lists active sessions without exposing token material, permits revoking only the caller's session IDs, and requires the current password plus CSRF protection to revoke other sessions. Reauthentication failures and revocation actions are audited. The interface reports timestamps and the current-session marker; it does not invent device or location details.

Candidate onboarding is private and keyed only by the authenticated user ID; an `initial_purpose` of employer does not prevent a user from also maintaining a candidate profile. Draft writes use version checks and a per-user row lock; completion requires a name and at least one target role, while skills are optional. Completion is repeat-safe, and completed drafts cannot be edited through onboarding. Labels are currently candidate-entered strings (up to five target roles and twenty skills) because no approved catalog contents were supplied; normalized roles/skills APIs remain separate work.

The candidate dashboard is a read-only aggregate over the authenticated user's existing onboarding, portfolio, projects, applications, saved jobs, invitations, and attempts. Employer-purpose identities need an existing candidate workspace; other users receive only their own counts. Public project totals exclude private drafts, pending invitations exclude expired records, and active attempt totals exclude submitted, completed, and cancelled attempts. The page does not display schedule, score, or evidence placeholders.

Organization creation is idempotent and creates a scoped `owner` membership in the same transaction. Workspace listing returns only the candidate workspace and organizations the user belongs to. Organization draft updates are locked and versioned; only `owner` and `admin` members can change or complete them. Membership APIs return minimal fields, enforce tenant and role boundaries, audit mutations, prevent removing the last owner, and never let admins grant or modify owner/admin roles. Invitations store only token hashes, expire after seven days, require a matching verified account, are single-use and cancellable, and return masked addresses. The acceptance token is sent in the JSON body rather than a URL path so server access logs do not capture it. Email delivery failure cancels the invitation; durable delivery retry/outbox processing remains unimplemented.

Project records store private, self-reported names, problem statements, contributions, technology labels, and strict GitHub repository-root links. Candidates assign a unique reserved-name-checked handle, consent to exposing their name/target roles/skills, and separately consent to each public project. A separate opt-in makes an already public profile searchable by eligible hiring teams; directory results contain only the fields already on the public profile. The public DTO excludes emails, internal IDs and private projects; links are served with `no-store`. Published projects cannot be edited or have links changed until unpublished. Unpublishing a portfolio also clears all project publication flags and discovery consent. Mutations are audited without logging project content. Handles do not yet have a moderation or impersonation-review workflow, so public profile launch needs that control. Delete is transactional and maps restrictive foreign-key references to `409`; source links cascade with their project. The competency catalog has eight stable Python/FastAPI entries. Project claims are stored as `self_reported`, `unreviewed`, `candidate_only` records with an explicit verification limitation. Editing withdraws old claims and creates replacements; neither public portfolios nor application snapshots expose them. They are not evidence that linked code exists or belongs to the candidate.

Applications require a verified user with a completed candidate workspace, a published job, an active public portfolio, explicit per-application consent, and an idempotency key. The transaction snapshots only the candidate’s public profile and individually published projects, plus the job text, organization name and current structured competency requirements. Private drafts, email and internal candidate/project IDs are omitted. A partial unique index permits one active application per candidate/job; a new request key after withdrawal permits reapplication. Applications are tenant- and role-scoped; organization owners/admins/recruiters can review active applications, while only owners/admins can record a final decision with a reason and human actor ID. Stage and decision changes are version-checked, audited and appended to an application event history. Candidate withdrawal hides the snapshot from employer endpoints; it does not erase the retained snapshot or recall information already viewed outside the service. All application read responses are `no-store`.

Job drafts accept up to eight unique, active catalog competencies with junior/mid/senior target level, deterministic-test and/or human-review acceptance, and a 1–3650-day freshness window. Self-reported claims cannot be accepted as proof. Existing job membership and recruiter+ write authorization apply. Job updates and application submission lock the job row, so the exact requirement list copied into an application cannot race with an update. Later requirement changes do not revise existing application snapshots. The deterministic report compares candidate-shared evidence to this frozen policy and returns demonstrated, insufficient, or unverified with explanations and source limitations.

Application snapshots are visible to organization owners/admins and the single recruiter explicitly assigned to that active application. Assignment requires an active same-organization owner/admin/recruiter, is versioned and audited, and is removed with an audit entry when a recruiter is demoted. Unassigned recruiters receive no application, invitation, or evidence-report details; final decisions remain owner/admin-only. Candidate evidence sharing is separately consented, versioned, application-scoped and revocable. Reviewer notes, custom pipeline stages, and retention/deletion controls are still pending.

Assessment authoring lets organization owners/admins/recruiters save versioned private drafts with a task, target competencies, allowed-tool declarations, and a weighted rubric. Each competency can optionally map to one active stable catalog ID; custom labels remain compatible. The mapping is stored in the definition and copied into immutable published versions, while unknown or duplicate IDs are rejected. Validation also requires unique competency and criterion names, rubric weights totaling 100, and every rubric criterion to map to a listed competency. Draft updates are optimistic-version checked. Publishing requires a verified owner/admin session and the explicit `assessment-review-v1` confirmation; it writes an immutable version snapshot and audit record. Assessment content is visible only to owner/admin/recruiter roles. The review actor is recorded, but a distinct reviewer and formal calibration have not been implemented. Assigned recruiters can invite an active applicant to an exact published assessment version with a 14-day expiry; owners/admins can also manage invitations. Candidate briefing responses expose the frozen task, rubric and function entrypoint, while private test inputs/expected values are stripped. Invitation and attempt consent are explicit, versioned, idempotent and audited; recording preferences are fixed off. Candidates can open a private single-file Python workspace after attempt consent. Saves are version-checked; bounded test runs execute a frozen source snapshot in a fresh rootless Podman container and expose per-competency counts only. The run record stores a source hash and hidden snapshots; passing competency groups create candidate-only, unreviewed deterministic-test evidence linked to that run. Test evidence is not yet shared with employers. Withdrawal and final human decisions transactionally cancel created, consented and active attempts; an in-flight run rechecks cancellation before recording evidence. Readiness checks consent, the presence of a private test suite and the local runner. Timed sessions, employer reviewer access to attempt details, evidence sharing/reporting, formal calibration and retention remain unimplemented. Rollback scripts for migrations 013–016 guard populated data/audit history; none were run against populated databases.

## Controlled Python assessment execution

Assessment definitions may contain an optional private `python_test_suite` with an entrypoint and up to six competency-linked JSON cases. Each case is limited to 8 KB. Candidate workspace writes are capped at 50 KB, optimistic-version checked, candidate-owned and `no-store`. Test-run requests use an idempotency UUID and accept no shell command or candidate-supplied tests; attempts are limited to ten runs. Run creation persists a source snapshot and SHA-256 before execution. The response contains only overall status and per-competency pass counts. Each competency result, including insufficient results, creates `candidate_only`, `unreviewed`, `deterministic_test` evidence linked to the run and frozen target level. Only passing results can satisfy the deterministic requirement; infrastructure failures create no evidence. Employer hiring decisions remain an authorized human action.

The local runtime uses the pinned Python 3.12 slim image in rootless Podman, UID 65534, no network, a read-only root, bounded temporary storage, dropped capabilities, no-new-privileges, 192 MiB memory, 0.5 CPU, 32 processes, and container timeouts. It does not mount host paths or receive host credentials. Candidate code is never executed in the FastAPI process. The implementation executes synchronously; stale runs are reconciled as infrastructure failures on a later status read or retry, not by a durable worker. Escape resistance is not verified, the container timeout exit mapping was verified only on local Windows Podman, and no retention policy exists for private source snapshots.

The OpenAPI document includes explicit request/response schemas, RFC 9457-style error media types, session-cookie and CSRF-header security schemes, and the tested operation responses. PostgreSQL migrations are versioned and startup applies them under an advisory lock. Registration and password-reset delivery failures are audited; registration reports a retryable error, while password-reset responses remain generic.

## Sequence and blockers

1. **Identity, account sessions and public metadata:** implemented and locally verified. Production activation is blocked on approved terms text/URL, live email-provider configuration, production database configuration, and shared secret setup.
2. **Candidate onboarding:** implemented and locally verified; completed drafts are private. Catalog-backed role/skill selection remains separate work.
3. **Organization onboarding and membership:** implemented and locally verified, including tenant-scoped member listing, invitations, membership role updates and removal.
4. **Evidence MVP foundation:** stable competency catalog, private self-reported project claims, versioned job requirements and application-time snapshots, and optional catalog IDs frozen into assessment versions are implemented and locally verified.
5. **Assessment attempt consent:** versioned acceptance/revocation, fixed-off recording preferences, audit history and cancellation of created/consented/active attempts are implemented and locally verified.
6. **Controlled assessment execution:** implemented as a single-function Python workspace with frozen suites, rootless Podman isolation, idempotent persisted runs, sanitized outputs and candidate-only evidence provenance. Execution is synchronous; there is no durable worker queue or escape review.
7. **Candidate evidence sharing and deterministic gap report:** implemented; candidate consent is application-specific, versioned and revocable. Reports disclose only selected evidence to organization owners/admins and the assigned recruiter, and compare verification method, proficiency and freshness against the frozen job requirements.
8. **Focused follow-up:** implemented in the employer report. It recommends an unused published assessment only when its private deterministic cases cover unresolved accepted competencies at or above target proficiency; it favors assessments covering more gaps with fewer focused cases and skips assessments already invited for the application.
9. **MVP operations gate:** verify migration recovery, retention/deletion, real email, accessibility, production secrets, sandbox monitoring and recovery before deployment.

The Pro portfolio builder, opt-in talent discovery, synchronous account data export, and shared rate limiting are implemented and locally verified. Data deletion is deferred until retention, legal-hold, and request-fulfillment policy is approved. The next monetization dependency is provider test-mode billing; provider and pricing policy still need to be set before checkout can be enabled. Operations blockers include approved terms, external SMTP, durable email retry/outbox processing, a durable assessment worker, retention cleanup for private code/evidence, public-handle moderation, reviewer notes, timed sessions, independent assessment calibration/review, project proof-reference deletion behavior, sandbox escape testing/monitoring, and full visual/accessibility verification. No production-readiness claim is made.

## Status vocabulary

- `IMPLEMENTED` / `FINALIZED`: code and an explicit API schema exist for the operation.
- `PASS`: the named check passed in the latest run; `NOT_RUN` is not implied success.
- `PLANNED` / `SCAFFOLD`: proposed inventory rows that still need a vertical slice.
- `DEFERRED`: an inventory operation intentionally replaced or postponed until its dependency is available; its current API disposition is documented in the row.
- A passing local slice does not remove the external production blockers above.
